# 战斗配置 Excel 工具：优化结果与结构评估

## 本次边界

本次改动集中在编辑器配置工具，不改战斗结算、存档、动画、镜头、单位资源绑定规则。配置流仍为：Excel编辑 → 只读校验与差异预览 → 经确认的原位SO更新 → 游戏读取SO。

## 已实现的配置体验

| 能力 | 当前行为 |
| --- | --- |
| 字段差异 | 显示具体字段的前后值；效果以effectKey匹配，新增、删除、修改、移动分开显示 |
| 关联差异 | 技能关联显示角色用途、顺序、ID和名称；删除关联不删除技能SO |
| 清空保护 | 清空已有普通技能列表、天赋行动或效果列表时，UI二次确认，服务层也要求显式确认 |
| 引用帮助 | RefUnits/RefSkills/RefBuffs显示ID、名称、来源和资产路径；子表引用列提供ID下拉 |
| 新配置引用 | 工作簿中尚未导入的主体覆盖SO的同ID名称，并加入辅助列表；下拉允许手填新ID |
| 更新辅助表 | 读取已保存工作簿，仅更新工具拥有的引用表、引用验证和辅助版本时间；保留业务单元格和额外计算表 |
| Unity查询 | 工作台按ID/名称/路径搜索现有资产，复制ID或定位；预览的新配置显示“待创建” |
| 语义提示 | 能量消耗超过基础上限、施加层数超过Buff上限、忽略的目标覆盖、缺少成长条目、空技能/空关联、默认普攻回点等提示为警告 |
| 安全导出 | UI覆盖确认；覆盖前检查目标未变化与占用，临时文件原子替换，旧Excel单独备份 |
| 元数据和历史 | 新导出文件记录项目标识、工作簿ID、版本、范围、生成时间和资产基线；导入保留带路径/hash/结果/资产变化的独立历史报告 |
| 批量制作 | 复制单位/技能、单体伤害/群体伤害/我方治疗/新单位普攻模板；预览后另存，不直接写SO |

## 代码职责

- `ConfigTableSchema.cs`：列结构、类型、DTO和扩展契约。
- `ConfigWorkbook.cs`：基础OpenXML读写、字段定位、类型检查和表格样式。
- `ConfigWorkbookReferences.cs`：引用辅助表、命名区域、ID下拉和保留用户表格的刷新流程。
- `BattleConfigTableAdapter.cs`：索引、身份、领域关联、成长保护、资产更新计划。
- `ConfigAuthoringSupport.cs`：可读差异、语义警告和资产查找。
- `ConfigBatchAuthoring.cs`：数据副本的模板/批量生成和相应编辑器窗口。
- `ConfigWorkbookFiles.cs`：工作簿安全发布与旧文件备份。
- `ConfigImportService.cs`：快照、过期检查、应用、资产备份恢复和历史。
- `BattleConfigImportWindow.cs`：用户操作入口；不承载游戏规则。
- `BattleConfigImportVerification.cs`：隔离资源验证与编辑器验证入口。

## 优点：为什么保留这一结构

### 1. 运行时和制作流程分开

运行时继续持有原来的UnitConfig、SkillConfig、BuffConfig引用。Excel故障不会变成游戏启动依赖，也没有引入新的运行时ID解析链。已有模型、成长和演出引用不会因为调倍率被重建。

### 2. 修改结果可以在写入前看见

解析和预览不修改SO。差异来自稳定身份，效果移动不再表现为整段列表文本替换。文件或资产在预览后变化会使计划失效，避免按旧预览覆盖新编辑。

### 3. 制作辅助和导入规则共用数据契约

模板生成普通业务行，然后通过同一套解析和验证。批量工具不能跳过关联、枚举、范围和成长保护。复制单位时同一技能在Normal和TalentAction中共用，只复制一次；不同新单位可拥有各自的技能副本。

### 4. 失败恢复覆盖真实文件和GUID

导入备份资产及meta，写入异常恢复原文件，并只清理本次创建的资产。导出备份旧Excel。两种备份用途不同：前者回退SO，后者找回表格内容。

## 不方便之处：现在仍然真实存在

### 1. 一个角色分散在多张表中

做一个角色需要在Units、UnitSkills、Skills、SkillEffects之间跳转。范式化关系对批量调数值有利，对逐个设计复杂角色不直观。引用表、名称搜索和模板减少抄ID，但不能替代“角色整体视图”。

后续最有价值的制作工具是：选中角色后，在一个视图展开其技能、效果、Buff和成长引用，保存仍走现有导入计划。无需推翻当前表结构。

### 2. Excel与Unity之间存在明确的编辑归属

Excel管理规则和基础值，Unity管理模型、头像、成长与演出。制作新角色仍要在两处工作，Excel也不能看到最终动画效果。为了避免无意复制另一个角色的成长或美术绑定，批量复制不会替你填这些引用。

工作台暂时提供定位入口，尚未提供集中显示“缺哪些资源”的角色完成度清单。

### 3. ID辅助列表是刷新快照

Excel里新增技能后，可立即手填其ID，但下拉不会在每次编辑时自动发现新行。需保存、关闭工作簿，点击“刷新工作簿引用辅助表”，然后重新打开。导入本身只需保存，通常无需关闭。

这是纯xlsx且不依赖宏/插件的代价。刷新只重建Ref*表和工具引用验证，不重建业务表。工具保留这三个辅助表名，不应把私人计算放进去。

### 4. 子列表采用完整替换

某个技能出现在Skills中，其SkillEffects必须完整；单位也是如此。复制一行主体却漏掉子表，会表达“清空”。现在会列明删除并要求确认清空，但仍需理解这项语义。

未来若要支持“仅改一个字段”的补丁表，必须另设明确的Patch模式；不能把同一个空白单元格同时解释成默认值、不修改和删除。

### 5. 批量复制还有作者决策

复制角色时要选择共用技能还是复制技能。共用适合怪物变种，但之后改技能会影响所有引用者；独立复制容易单独调节，但会产生更多重复数据。复制出的effectKey属于新技能，成长配置需重新绑定。模板也只是规则起点，不代表近战位移、弹道或技能动画已经完成。

### 6. 资产索引较宽，预览容易失效

索引指纹涵盖范围内配置及跨范围成长依赖。即使修改了一个看似不相关的配置，也可能要求重新预览。它优先保证安全；更细的依赖指纹能改善体验，但需要维护可靠的引用图。

### 7. 扩展接口尚不是任意模块插件平台

IConfigTableAdapter可以声明表、解析、验证和生成自定义更新操作；但ConfigAssetIndex仍明确理解Unit/Skill/Buff，默认应用路径也知道技能效果和单位技能列表。接入装备/天赋时可以用CustomApply扩展，仍需编写模块索引、备份范围与依赖校验，不能只加一张Excel表。

当前字段映射使用反射和字符串字典，避免重复映射代码，但重命名字段后无法全部靠编译器发现。扩表时必须补相应验证；规模增长后适合引入强类型DTO或代码生成，不应提前把整个战斗数据层重写。

### 8. 这不是数据库事务，也不是Unity Undo

资产应用有文件级备份恢复，不承诺AssetDatabase事务。恢复一个旧备份会覆盖其后对相同资产的修改，需审阅范围。不能通过Ctrl+Z回退整次导入。历史报告记录结果，初始导出元数据不等于可自动合并双方变更的三方合并系统。

### 9. xlsx不便于Git审阅和多人协作

虽然导入历史可读，Excel二进制文件本身仍不适合逐行diff或自动合并。多人制作时应约定负责范围；未来可以增加确定性文本快照供代码审查，Excel继续供制作人员编辑。

## 后续建议顺序

1. 先用一个完整新敌人走通模板→改数值→导入→绑定表现→战斗试玩，积累真实制作问题。
2. 做角色整体配置视图与资源缺失清单，减少跨表/跨窗口查找。
3. 做“谁引用了这个技能/Buff/effectKey”的依赖查看，辅助共享技能决策。
4. 团队规模或数据量增长后，再做文本快照、细粒度预览指纹、强类型模块适配。

不建议现在引入自动双向同步、运行时Excel加载或通用配置数据库；它们会让当前最需要的制作流程更难理解。
